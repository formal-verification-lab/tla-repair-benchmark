# TLA+ Repair Benchmark

Курсовая работа, вариант №2: сравнение полного лога, фильтрованного лога и
объяснения LLM при исправлении спецификаций TLA+.

Реализованы общие контракты, CLI, клиент Ollama с сохранением вызовов и
подготовка локального пилота LoRA. Модель основных экспериментов ещё не выбрана.
Основные 12 прогонов курсовой пока не проведены.

## Установка и проверка кода

Требуется Python 3.12 или новее:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
tla-repair schema-info
ruff check .
ruff format --check .
pytest
```

CI проверяет обычный Python-код на Linux с Python 3.12/3.13; обучение использует
отдельное окружение MLX на Apple Silicon. Java нужна для проверок спецификаций.

## Локальный пилот дообучения

База: `mlx-community/Qwen2.5-Coder-3B-Instruct-4bit`, ревизия
`3dd939c621c08e5753d5b89f35a2642cd83b98ca`. Используется 4-битный MLX checkpoint,
а не GGUF из Ollama. Настройки находятся в `configs/lora-pilot.json`, точные
версии зависимостей — в `requirements-mlx.txt`.

Подготовка на новой машине:

```sh
python3.12 -m venv .venv-mlx
.venv-mlx/bin/python -m pip install -r requirements-mlx.txt
.venv-mlx/bin/python -m pip install -e .
.venv-mlx/bin/python -m benchmark.finetune prepare
.venv-mlx/bin/python -m benchmark.finetune smoke
```

`prepare` загружает закреплённые веса и официальный `tla2tools.jar` с проверкой
контрольной суммы, создаёт синтетические данные и проверяет их SANY/TLC.
У корректных модулей проверяется также ожидаемое число состояний. Внесённые
ошибки должны действительно обнаруживаться инструментами. Вывод инструментов
сохраняется; частично подготовленный набор не допускается к обучению.

Корпус содержит 32 параметризованные системы: 24 обучающие, 4 валидационные и
4 тестовые. Из каждой получаются четыре записи: генерация, исправление по
полному логу, исправление по диагностической части и объяснение без кода.
Всего 96/16/16 записей. Разделение выполнено по шаблонам задач; это небольшой
синтетический набор с общими примитивами, а не независимый промышленный benchmark.
Синтаксические и простые диагностические ошибки не покрывают весь класс ошибок TLC.

Генератор не читает каталог основных задач, их Gold или предыдущие ответы LLM.
До использования адаптера в курсовой нужно выбрать четыре задачи и проверить,
что они и близкие варианты не попали в обучающий набор. Данные для обучения
и синтетической проверки не являются обязательными четырьмя задачами курсовой.

`smoke` выполняет один шаг с самым длинным обучающим примером и проверяет
конечность весов адаптера. Он проверяет работоспособность, а не качество модели.
Длинные примеры отклоняются до запуска; тихое обрезание запрещено.

После успешной короткой проверки длительный запуск выполняется одной командой
из корня репозитория:

```sh
caffeinate -i .venv-mlx/bin/python -m benchmark.finetune train
```

Команда последовательно оценивает исходную модель, обучает адаптер 200 шагов,
затем повторяет оценку с адаптером. Шаги оптимизатора не являются итерациями
генерации из задания. Обучение начинается с базовой модели; короткий тестовый
адаптер и предыдущие запуски не подхватываются автоматически.

Настройки для пилота: batch size 1, LoRA rank 8, последние четыре слоя,
learning rate 1e-4, gradient checkpointing и loss только по последнему ответу.
Финальная оценка использует один и тот же отложенный набор и greedy decoding;
проверяются генерация, исправление по полному логу и формат объяснений.
Правильность текстовых объяснений автоматически не оценивается. Число состояний
помогает заметить упрощение модели, но не доказывает семантическую эквивалентность.

Каждый запуск получает отдельный каталог `runs/lora-pilot-…`: снимок параметров,
хеши входов и кода, версии пакетов, логи, память MLX, адаптер и результаты
`baseline/` и `adapted/`. `complete.json` появляется только после завершения всех
этапов; при сбое сохраняется `failed.json`. Скрипт останавливается при изменении
входных файлов или нечисловых весах/потере. Во время запуска сохраняйте эту
рабочую копию кода: проверка не допускает смешения версий до и после обучения.

Подготовленные данные и веса находятся в `data/lora-pilot/`, результаты — в
`runs/`. Они игнорируются Git; завершённые запуски не перезаписываются. Публикация
весов или данных автоматически не выполняется. MLX-адаптер пока используется
для локальной оценки; подключение к основному runner требует отдельной проверки.

## Исправление собственных генераций

После завершённого `train` можно проверить, исправляет ли адаптер собственные
ошибки. Передайте каталог завершённого обучения:

```sh
.venv-mlx/bin/python -m benchmark.self_repair \
  --training-run runs/lora-pilot-20261101T212351Z-9d1c7f \
  --max-attempts 3
```

Скрипт повторно проверяет сохранённые первоначальные генерации из `adapted/`,
затем передаёт полный фактический лог ошибки в изолированную историю каждой
задачи. Эталонные ответы и искусственно испорченные примеры в запросы не входят.
Первая генерация считается попыткой №1, поэтому лимит 3 разрешает максимум два
обращения для исправления; допустимый общий лимит — от 1 до 10. Нового обучения
нет. Промпты, ответы, логи, токены, время и хеши входов сохраняются в отдельном
каталоге `runs/self-repair-…`.

При успехе TLC задача завершается; ожидаемое число состояний записывается только
для анализа и не передаётся модели. Тайм-аут верификатора и превышение окна
8192 токена учитываются отдельно от исчерпания попыток. История не обрезается.
Это диагностическое продолжение пилота на уже просмотренных четырёх случаях из
двух синтетических семейств, а не новые независимые задачи и не сравнение трёх
методов курсовой. Успех TLC требует последующей проверки соответствия заданию.

В локальном запуске `self-repair-20261101T214913Z-86ab5e` ни одна из четырёх
собственных генераций не прошла TLC за три попытки. Два случая Mutex повторяли
исходный ответ без изменений, два случая Handshake сохраняли ошибки синтаксиса.
Успех 4/4 на исправлении заранее внесённых ошибок из предыдущего пилота не
подтвердился для собственных ошибок. Текущий адаптер пока не выбран для основных
экспериментов курсовой.

## Клиент Ollama

Ollama остаётся дополнительным интерфейсом для установленных в нём моделей:

```sh
tla-repair ollama-chat --help
ollama list
```

Для вызова обязательны `--model` с точным установленным тегом, `--messages` с
JSON-массивом объектов role/content и `--output` с каталогом артефактов.
Клиент сам не скачивает модели. История передаётся явно; скрытых повторов нет.
Записываются точный запрос, исходный ответ, токены, время, версия сервера и
метаданные модели с digest. Для фиксации весов предусмотрен `--expected-digest`.

Автоматическое обрезание и сдвиг контекста отключены. При известных счётчиках
проверяется сумма входных и выходных токенов относительно `num_ctx`; это проверка
после генерации, поскольку MLX-бэкенд Ollama 0.40.7 мог игнорировать заданное окно.
Пустые завершённые ответы возвращаются для учёта попыток; `done_reason` и thinking
сохраняются в исходном ответе. Успех генерации не означает успех SANY/TLC.

Контракты модулей и учёта артефактов: `docs/contracts.md`.
