# Метрики из сохранённых артефактов

`benchmark.metrics` читает общий формат `CallRecord` / `AttemptRecord` и
`VerificationResult` версии 1.0.0. Он не запускает LLM или Java, не читает Gold,
не правит исходные результаты и не создаёт runner.

```sh
python -m benchmark.metrics \
  --experiment results/<experiment-id> \
  --output runs/summary-001
```

Выходной каталог должен быть новым. После проверки входов создаются
`summary.json` с полными метриками и `branches.csv` с основными показателями
каждой наблюдаемой ветви. CSV содержит идентификаторы задачи/повторения/метода,
число попыток, первые успехи SANY/TLC, успех, исходный успех и исход ветви.
Детальные расходы и категории ошибок находятся в JSON.

## Входные данные и проверки

Нужен `manifest.json` с `schema_version` и `phase` (`pilot` / `main`);
`experiment_id` переносится в сводку, если задан. Агрегация не удостоверяет
полноту исследовательского manifest: её отдельно проверит этап валидации стенда.
Пилотные и основные данные не объединяются: один запуск читает один корень.

Расположение записей соответствует `docs/contracts.md`:

```text
calls/<call-id>/record.json
tasks/<task-id>/repeat-01/A/attempt-01/record.json
```

Аналогично B/C. Читаются только записи и явно указанные в них файлы запросов,
ответов, спецификаций, проверок и обратной связи. Не выполняется обход `reference/`.
Пути должны быть относительными корню; выход через `..`, абсолютный путь или
символическую ссылку отклоняется. Отсутствующие файлы прерывают расчёт.

Проверяются версии схемы, целочисленные токены, конечные неотрицательные времена,
идентичность записи её каталогу, ссылки на вызовы и их назначение, соответствие
задачи/повторения/метода. Номера попыток идут подряд от 1 до 10; продолжение после
успеха отклоняется. Первая попытка A/B/C должна ссылаться на одну исходную
генерацию, спецификацию и проверку. Ремонтные вызовы не переиспользуются между
попытками. Для C требуется ссылка на отдельный, не переиспользованный
вызов объяснителя.

Фактический расход берётся из CallRecord, который должен сохранить runner.
Копии response.json в артефактах стратегий не считаются новыми вызовами.
Запрос/ответ проверяются на наличие и читаемость JSON, но агрегатор не пытается
заново интерпретировать разные провайдерские форматы usage: нормализованный usage
в CallRecord должен соответствовать сохранённому ответу клиента.

## Попытки, успех и ошибки

- `sany_first_pass` / `tlc_first_pass`: номер первой успешной проверки или null.
- `iterations_total`: число наблюдаемых попыток основной модели, включая общую
  начальную попытку. Вызовы объяснителя не добавляют попытки.
- `success`: последняя наблюдаемая попытка прошла SANY и TLC.
- `initial_success`: обе проверки пройдены с первой попытки. Такой случай
  исключён из `repair_eligible_observed` и успехов исправления.
- `error_types`: только автоматические категории `spec_error` из верификатора;
  отсутствующая категория — `unknown`. Ручная переоценка не подмешивается.
- `tool_status_counts`: статусы обоих инструментов, включая timeout, tool_error
  и not_run. Технические сбои не добавляются к ошибкам спецификации.

Исход ветви (`outcome`): `success`, `technical_interruption` при техническом
результате последней проверки, `exhausted` после 10 неуспешных попыток без
технического завершения или `unresolved` при меньшем числе попыток без успеха.
Это наблюдаемые исходы: без записи завершения runner нельзя объявить короткую
ветвь окончательной неудачей. Для пилота с лимитом меньше 10 завершённая
неуспешная ветвь пока будет `unresolved`.

По каждому методу показаны численность, исходные успехи, кандидаты на исправление,
успехи исправления и исходы. `success_rate_observed` относится только к имеющимся
ветвям и не является итоговой оценкой всего запланированного эксперимента.
`missing_method_branches` показывает недостающие A/B/C для наблюдаемых пар
«задача/повторение»; полностью отсутствующие задачи по нему определить нельзя.

`iterations_mean_all_observed` включает все имеющиеся ветви.
`iterations_mean_successful_only` и медиана `iterations_median_successful_only`
явно относятся только к успешным; при отсутствии успехов они равны null.
Неуспешные и незавершённые ветви остаются в подробной таблице.

## Токены, время и технические события

Завершённые обращения учитываются по уникальному call_id, включая обращения,
пока не связанные с попытками. `completed_calls` разделяет initial, repair и
explanation. `completed_calls_total` — общий расход завершённых обращений.
Общая начальная генерация оплачивается один раз и не распределяется по методам.
В ветвях и сводках методов приведены только их repair и explanation отдельно.
Несвязанные генерации и неиспользованные объяснения перечислены отдельными ID.

Для каждого набора обращений сохраняются:

- `calls`: число обращений/событий в этом наборе;
- `input_tokens`, `output_tokens`, `duration_seconds`: полный итог или null,
  если хотя бы одно слагаемое неизвестно;
- поля с суффиксом `_known_sum`: только известная часть суммы;
- поля `_unknown_count`: число отсутствующих значений.

Нулевое число обращений даёт измеряемый итог 0; неизвестный расход отдельного
обращения не заменяется нулём. Стоимость оставлена null: подтверждённые тарифы
на вход не передавались, поэтому денежные затраты не вычисляются.

`calls/*/error.json` учитываются отдельно в `technical_failed_calls`, с известными
usage и временем. Событие не создаёт попытку; отсутствие usage остаётся неизвестным.
`completed_and_failed_events_total` показывает совместный итог записанных
завершённых вызовов и технических событий. Ошибка может произойти до отправки
запроса, поэтому число событий не доказывает число оплаченных запросов или
повторных сетевых обращений. Пока общий формат событий не содержит контекста
задачи и метода, эти ошибки нельзя достоверно распределить по ветвям; агрегатор
этого не делает. Одновременный completed record и error одного ID отклоняется.

Время Java суммируется по уникальным путям verification: общий исходный результат
не утраивается. Есть отдельные `sany_seconds_unique` / `tlc_seconds_unique`.
Время проверки в отдельной ветви включает её исходную проверку и предназначено
для анализа ветви; складывать его по A/B/C как фактические затраты нельзя.
Сумма длительностей компонентов не является общим календарным временем при
параллельном выполнении.

## Воспроизводимость и ограничения

Сводка хранит SHA-256 всех прочитанных входных файлов и исходного кода агрегатора.
Изменение прочитанного файла во время расчёта отклоняется. Для согласованного
снимка следует использовать остановленный запуск: агрегатор не блокирует runner
и не обнаруживает появление новых файлов после начала обхода.

Тесты используют явно синтетические артефакты; это не данные эксперимента.
Проверяются общий исходный вызов, объяснитель, неизвестный usage, технические
события, неполные ветви, лимит 10, различие средних по всей/успешной выборке,
неверные ссылки и схемы, выход за корень, отсутствие чтения Gold и перезаписи.

Основной runner ещё должен записывать контекстные CallRecord/AttemptRecord;
существующие клиентские артефакты без них недостаточны для такой агрегации.
Если в `calls/` есть каталог без CallRecord и без технического error.json,
расчёт отклоняется, чтобы не выдать незарегистрированный расход за нулевой.
Код не создаёт недостающие записи и не выдаёт пилотные результаты за основную
серию. Реальные таблицы исследования и графики появятся после основных прогонов.
