# Три метода обратной связи

`benchmark.feedback` реализует общий `FeedbackStrategy.build(specification,
verification) -> FeedbackResult`. Новый клиент провайдера и runner не создаются.
Методы в коде называются A/B/C; C соответствует методу «В» в плане.

## Использование

```python
from pathlib import Path
from benchmark.feedback import FullLogStrategy, FilteredLogStrategy, ExplanationStrategy

# attempt_root — каталог артефактов текущей попытки.
# client и settings — тот же LLMClient и ModelSettings, что у основной модели.
strategies = {
    "A": FullLogStrategy(attempt_root),
    "B": FilteredLogStrategy(attempt_root),
    "C": ExplanationStrategy(attempt_root, client, settings),
}
feedback = strategies[method].build(specification, verification)
# Основной модели передаётся ровно feedback.text.
```

Клиент по-прежнему сам сохраняет вызов в `calls/<call_id>/`. Для GigaChat следует
использовать существующий `GigaChatClient` с зафиксированной версией модели.
Стратегия копирует настройки при создании и перед каждым вызовом. Она не меняет
модель, параметры, лимит попыток и не обращается к Gold. Совпадение настроек
объяснителя с основной моделью обеспечивает передача одних и тех же настроек
при интеграции runner.

## A: полный лог

Версия `full-log-v1`. Передаются stdout и stderr обоих инструментов в порядке
SANY stdout, SANY stderr, TLC stdout, TLC stderr. Каждый блок имеет явное имя;
перед инструментом указан его статус, включая `not_run` для пропущенного TLC.
Текст каждого потока сохранён без изменений. Между блоками добавляется перевод
строки, если его не было; порядок чередования stdout/stderr во время процесса
из отдельных потоков восстановить нельзя.

## B: автоматическая фильтрация

Версия `diagnostic-prefix-v1`. Каждый поток обрабатывается отдельно:

1. Находится первая строка с error, exception, warning, abort, deadlock,
   violat, заголовком состояния/возврата в состояние или кодом ошибки TLC.
2. До неё удаляются только строки, целиком соответствующие известным шаблонам
   служебного вывода: версия, режим обхода, прогресс, старт/финиш, статистика.
   Стандартная рекомендация TLC о throughput GC и строка о `-nowarning`
   также считаются служебными и не начинают диагностический блок.
3. Начиная с первой диагностической строки сохраняется весь оставшийся поток,
   включая позиции, все состояния, замыкание цикла и заключительные сообщения.
4. Если диагностическая строка не найдена, поток возвращается без изменений.

Неизвестные строки не удаляются; ограничения длины нет. Фильтр не добавляет
советы или собственную интерпретацию. Он намеренно консервативен: большой
контрпример может остаться большим, а неизвестный формат — полным логом.
Исходные потоки сохраняются отдельно независимо от фильтрации.

## C: объяснение модели в новом контексте

Версия `explanation-verbatim-v1`. На каждый вызов создаются ровно два новых
сообщения: фиксированный системный промпт `EXPLANATION_PROMPT` и пользовательское
сообщение с текущей спецификацией и полным логом. Предыдущие ответы, история
ремонта, описание задачи, cfg и Gold дополнительно не передаются. Содержимое cfg
может присутствовать только как часть фактической диагностики инструмента.

Промпт просит объяснить ошибки и необходимые исправления словами, без кода.
До основных запусков фиксируется следующее правило ответа:

- Ответ передаётся основной модели дословно, без дополнений и переписывания.
- Пустой ответ тоже сохраняется и передаётся; повторного вызова нет.
- Ответ с кодом не редактируется и не вызывает повтор. Ставится флаг
  `code_detected`, который следует отдельно учитывать при анализе нарушений
  формата. Детектор эвристический: fences, MODULE, VARIABLES/EXTENDS или `==`.
  Флаг не доказывает наличие или отсутствие полноценной спецификации.

Эта политика позволяет восстановить фактическое влияние ответа. Она не
гарантирует, что объяснитель соблюдёт запрет кода; такие случаи требуют отдельного
анализа. Изменение политики/промпта после пилота требует новой версии протокола.

## Артефакты и учёт

Каждый вызов создаёт новый `feedback/<uuid>/` внутри переданного корня:

- `verification.json`, `sany.stdout.log`, `sany.stderr.log`, аналогичные файлы TLC:
  исходные результаты проверки. Тексты сохраняются без изменения переводов строк.
  Точные исходные байты Java остаются в артефактах верификатора.
- `policy.json`: применённая версия правил.
- `feedback.json`: точный `FeedbackResult`, включая реально передаваемый текст.
- Для C — `request.json` с сообщениями/настройками, `response.json` с полным
  `LLMResponse`, usage, временем, моделью и сырым ответом клиента; `format.json`
  с флагами формата. `explanation_call_id` связывает результат с вызовом клиента.

Caller задаёт корень текущей попытки, сохраняет ссылку на её feedback.json в
`AttemptRecord` и дополняет вызов отдельным `CallRecord` с purpose `explanation`,
task_id, repetition и методом C. Файл `response.json` стратегии является копией
сведений о вызове, а не новым платным обращением: учёт ведётся по уникальному
call_id. Объяснитель не увеличивает число попыток основной модели; его обращения
и расход показываются отдельно. Создание этих контекстных записей — задача runner.

Техническая ошибка LLM пробрасывается без повторов; запрос и тип ошибки
сохраняются, успешный feedback.json не создаётся. Подробная диагностика API
остаётся в артефактах существующего клиента. Ошибка записи останавливает работу.
Повторный build создаёт новый каталог, существующие результаты не перезаписывает.
Маршрутизация технических ошибок Java и таймаутов также остаётся задачей runner;
наличие стратегии не означает разрешение считать их ошибками спецификации.

## Проверки

Тесты проверяют неизменность полных логов, CRLF, неизвестную диагностику, позиции,
контрпример на 5000 состояний с возвратом к первому, независимые контексты,
неизменность настроек, ответы с кодом/пустые ответы, отсутствие повторов,
сохранение usage и остановку при ошибках записи/API. Интеграционный тест использует
существующий GigaChatClient и локальный HTTP-сервер; реальный API не вызывается.

```sh
pytest tests/test_feedback.py tests/test_gigachat.py
```

Основные эксперименты и оценка качества объяснений этим этапом не выполняются.
