# Проверка стенда перед основными экспериментами

Текущий этап проверяет совместимость имеющихся модулей и формат фиксации
протокола. Он **не завершает допуск к основным экспериментам**: на момент
начала ветки в main отсутствуют основной runner участника 1 и общий сквозной
пилот. Базовая ревизия — `ac94aff` (слияние PR с метриками).

## Выполненная часть

- Проверены общий исходный вызов A/B/C и отдельный учёт объяснителя в метриках.
- Проверены свежие контексты объяснителя и работа существующего GigaChatClient
  с локальным HTTP-сервером (без реального API).
- Проверена граница `load_inputs`: описания и cfg доступны, чтение reference/
  запрещается тестами. Это проверка компонента, не доказательство поведения runner.
- Добавлен связующий тест с настоящим JavaVerifier: TLC выдаёт нарушение
  инварианта с двумя состояниями; A/B сохраняют весь диагностический суффикс
  и оба состояния. Обратная связь, ссылка на объяснение и контекстные записи
  передаются агрегатору, который считает initial один раз и объяснителя отдельно.
- В том же тесте корректные спецификации действительно проверяются SANY/TLC.
  Их исправления заданы тестом, ответы объяснителя и API-записи синтетические:
  это не качество LLM и не пилот основного runner.
- CI Java job запускает связующий тест. Установка зависимостей ограничена
  пятью минутами, каждый job — 15 минутами; скачивание JAR имеет сетевые лимиты.

## Снимок протокола

Добавлен отдельный профиль manifest `benchmark-snapshot-v1`. Это уточнение
общего контракта для review и подключения основного runner, а не изменение
существующих CallRecord/AttemptRecord или самостоятельный runner.

`configs/protocol-snapshot.example.json` — **незаполненный пример**, который
заведомо не проходит проверку. Значения null и пустые mappings нужно заполнить
по фактическому окружению и результатам согласованного пилота. Таймауты 30/60
секунд и имя семейства GigaChat в примере взяты из текущего проекта и не являются
доказательством выбора версии модели или финальных настроек.

Каталог снимка содержит manifest.json и копии перечисленных в нём файлов.
Пример структуры:

```text
snapshot/
  manifest.json
  code/runner.py
  code/... остальные участвующие модули ...
  prompts/system.txt
  prompts/initial.txt
  prompts/repair.txt
  prompts/explanation.txt
  tasks/selection.json
  tasks/<task-id>/description.md
  tasks/<task-id>/Spec.cfg
  tools/tla2tools.jar
```

Gold в этот снимок не включается; отдельный офлайн-аудит подготовленного
набора должен проверить его совместимость с cfg. Снимок хранится локально в
игнорируемом data/ или runs/: описания задач не публикуются автоматически.

```sh
python -m benchmark.validation \
  --snapshot runs/protocol-snapshot-001 \
  --output runs/protocol-validation-001.json
```

Результат не перезаписывается. Код 0 означает только успешную проверку снимка;
код 1 — найденные нарушения. Поле `main_readiness` всегда `not_assessed`:
валидатор не заменяет review, пилот и проверку runner.

### Поля manifest

- `schema_version`, `validation_profile`, `experiment_id`, `phase`,
  `created_at_utc`: версия, идентификация, разделение pilot/main, UTC-время.
- `code`: полный revision SHA, dirty=false, runner_path, source_files.
  `source_files` — mapping относительного пути архивного исходника в SHA-256;
  runner_path должен входить в него. Владелец runner включает весь используемый
  код; валидатор проверяет перечисленные файлы, но не вычисляет зависимости
  модулей и не доказывает соответствие архива записанному Git-коммиту.
- `model`: provider, requested_id, resolved_id, непустые явные parameters.
  Версия должна быть реально получена от клиента в пилоте; статическая проверка
  не обращается к провайдеру и не подтверждает достоверность указанного ID.
  Допустимость параметров конкретному провайдеру по-прежнему проверяет клиент.
- `environment`: фактические версии Python, Java и tools. `verifier`: путь
  архивного JAR, SHA-256, java_executable, таймауты SANY/TLC, tlc_arguments.
  Разрешены только пары -workers/-seed, как в JavaVerifier; JAR сверяется с
  закреплённой конфигурацией задач.
- `protocol`: A/B/C, максимум 10 попыток включая начальную, общий initial,
  изолированные истории, запрет Gold, 1 или 3 повторения; новый контекст
  объяснителя с той же моделью, отдельный учёт его вызовов и текущие правила
  обработки кода/пустого ответа. Здесь же явно фиксируются политики сбоев API,
  проверок и переполнения контекста, версии фильтра и объяснителя.
- `prompts`: system, initial, repair, explanation — path и sha256 каждого
  точного шаблона. explanation должен побайтово совпадать с EXPLANATION_PROMPT.
- `tasks`: selection_path/selection_sha256 и inputs для всех четырёх task_id
  с description_path/cfg_path. Их содержимое сверяется с хешами выбора задач.

Валидатор читает только перечисленные файлы. Абсолютные пути, выход за корень,
внешние символические ссылки, reference/ и gold-check/ отклоняются. Хеши
прочитанных файлов и кода валидатора включаются в отчёт. Проверять нужно
остановленный снимок: изменение файла при чтении отклоняется, но процесс
не блокирует параллельного писателя и не удостоверяет историческую неизменность.

## Что остаётся проверить после появления runner

1. Интеграционные тесты **на самом runner**, а не на тестовой сборке записей:
   одна исходная генерация на задачу/повторение, одинаковый initial A/B/C,
   независимые истории, лимит 10 с учётом первой попытки.
2. Запрет доступа к Gold в процессе формирования всех основных запросов;
   основная модель получает только описание/cfg и разрешённую обратную связь.
   Запрет чтения reference/ должен действовать при тестовом запуске runner.
3. Соответствие фактических запросов и feedback.json, новый контекст объяснителя
   при каждом обращении, отсутствие ручных подсказок и скрытого усечения истории.
4. Полнота цепочек CallRecord/AttemptRecord, сырых ответов, логов и usage;
   обработка сбоев, остановка при ошибке записи, запрет перезаписи результатов.
5. Общий сквозной пилот участника 1 на одной задаче всеми методами с реальным
   выбранным API и Java. При исходном успехе отдельно продемонстрировать путь
   исправления на пилотном примере, не менять основные спецификации вручную.
6. Проверить таблицы метрик по артефактам пилота; зафиксировать точную версию
   модели, промпты, настройки, правила фильтрации и сбоев. После review сохранить
   полный снимок чистой ревизии и пройти статическую проверку выше.
7. Только после этого выполнять основные 12 прогонов, включая шесть участника 2.
   Пилот и основная серия имеют отдельные каталоги и phase в manifest.

Неизменность истории и отсутствие Gold в промптах нельзя доказать по одним
булевым полям manifest. Статическая проверка проверяет согласованность заявленного
протокола и хеши входов; поведение подтверждается тестами runner и пилотом.

## Команды проверки

```sh
pytest tests/test_validation.py tests/test_feedback.py tests/test_metrics.py \
  tests/test_task_dataset.py tests/test_gigachat.py
TLA_TOOLS_JAR=/absolute/path/tla2tools.jar pytest tests/test_benchmark_validation.py
```

Без TLA_TOOLS_JAR связующий Java-тест явно пропускается. Реальный API эти команды
не вызывают и ключей не требуют.
