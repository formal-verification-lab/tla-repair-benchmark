# Запуск эксперимента

`benchmark.runner.Runner` использует общий LLMClient, JavaVerifier и три стратегии
из `benchmark.feedback`. CLI `benchmark.experiment` подключает GigaChat и четыре
подготовленные задачи. Настройки находятся в `configs/experiment.json`; секреты
читаются из существующего внешнего файла или `GIGACHAT_CREDENTIALS`.

## Пилот

Из корня репозитория с чистой сохранённой ревизией:

```sh
.venv/bin/python -m benchmark.experiment \
  --phase pilot --task medium_01 --max-attempts 3
```

Без `--task` выполняются все четыре задачи; параметр можно повторить для выбора
нескольких задач пилота. Предел включает исходную генерацию. `--output` задаёт
новый каталог; по умолчанию создаётся уникальный `results/pilot-…`.
Пилотные ответы и ошибки не становятся результатами основной серии.

По умолчанию используются подготовленные `data/tasks/`, закреплённый JAR из
`data/lora-pilot/`, ключ и CA bundle из `~/.config/tla-repair/`. Пути можно
передать явно; `--help` перечисляет параметры. Код сам не покупает пакеты и
не переключает модели.

## Ветви и учёт

Один вызов генерирует исходную спецификацию для задачи и повторения. Она один раз
проверяется, затем все A/B/C ссылаются на те же call_id, файл и проверку. Истории
ремонта независимы; исходный успех завершает сразу все три ветви без исправлений.

Каждая последующая попытка получает только предусмотренную методом обратную
связь. Объяснитель C использует тот же клиент и настройки в новом контексте:
системная инструкция, спецификация и полный лог. История задачи, описание и cfg
отдельно ему не добавляются. Все объяснения регистрируются как отдельные
CallRecord. Девять исправлений C допускают до девяти вспомогательных обращений;
они не считаются попытками основной модели. Это явно выбранная трактовка лимита.

Из ответа выделяется содержимое единственного блока Markdown, если он один;
иначе текст передаётся проверке целиком. Никаких исправлений кода не выполняется.
Исходный ответ сохраняется, преобразование помечается в `extraction.json`.
Правило одинаково для всех методов. Формат объяснений контролируется существующей
стратегией: пустые ответы и код передаются без изменения с диагностическим флагом.

## Сбои

- Ошибка API останавливает запуск без скрытого повтора. Уже полученное объяснение
  остаётся учтённым даже при неудаче следующего исправления.
- Timeout/tool_error верификатора завершает затронутую ветвь как техническую;
  модель не получает просьбу исправить такой сбой.
- Ошибка записи останавливает запуск. Завершённые данные не перезаписываются.
- История не обрезается и не сбрасывается. Ошибка API о переполнении контекста
  сохраняется как технический сбой.
- Несовпадение фактической версии модели с закреплённой останавливает запуск;
  ответ и доступный usage сохраняются клиентом.

## Артефакты

Каталог содержит неизменный manifest, архив Python-кода, промптов, JAR, выбора
задач и только входных description/cfg. Gold не читается при сборке снимка и
запросов. Для происхождения исходных данных сохранены ссылки и хеши выбора задач.
На каждый вызов записывается CallRecord, на каждую проверенную версию —
AttemptRecord; сырые клиентские и Java-артефакты остаются рядом. Завершение каждой
ветви находится в `completion.json`, всего запуска — в `complete.json`.
`failure.json` означает остановку после начала выполнения; незавершённый каталог
без complete также нельзя считать законченным экспериментом.

В конце сохраняется `metrics.json`, вычисленный модулем коллеги непосредственно
по фактическим записям. При желании CSV можно получить отдельно:

```sh
.venv/bin/python -m benchmark.metrics \
  --experiment results/pilot-... --output runs/pilot-summary
```

При лимите пилота меньше 10 агрегатор помечает короткую неуспешную ветвь
`unresolved`; configured limit и фактическое завершение `attempt_limit` указаны
в manifest и completion. Это не неуспех в пределах десяти попыток.

## Основная серия

После проверки runner и реального пилота можно выполнить:

```sh
caffeinate -i .venv/bin/python -m benchmark.experiment \
  --phase main --pilot results/pilot-...
```

Основной запуск требует четыре задачи, предел 10, завершённый совместимый пилот,
те же код, модель, параметры, промпты, выбор задач и JAR. В настройках допустимы
одно повторение (12 ветвей) или три (36). Текущая конфигурация задаёт одно.
Перед первым API-вызовом полный снимок проходит `benchmark.validation`.
Успех статической проверки не заменяет review и аудит поведения runner.
Эта команда не выполняется автоматически после пилота.

Для повторения после сбоя нужен отдельный каталог: автоматического восстановления
нет. Предыдущие частичные данные остаются доступными для анализа; их нельзя
незаметно объединять с новым запуском или выдавать за завершённую серию.
