# Контракты и формат артефактов, версия 1.0.0

Источник Python-типов — `benchmark.contracts`. Версия сериализованных записей
задаётся полем `schema_version`. Это контракт для разработки; реализация записи
и чтения артефактов появится в runner, агрегация — в модуле метрик.

## Интерфейсы

- `LLMClient.generate(messages, settings)` возвращает `LLMResponse` либо
  выбрасывает `LLMCallError` при техническом сбое. История передаётся как tuple
  неизменяемых `Message`; клиент не должен незаметно вести общий чат.
- `Verifier.verify(spec_path, cfg_path, settings, work_dir)` возвращает
  `VerificationResult`. `work_dir` изолирован для каждой проверки. После
  неуспешного SANY результат TLC имеет статус `not_run`.
- `FeedbackStrategy.build(specification, verification)` возвращает
  `FeedbackResult`. Клиент, настройки и хранилище объяснителя передаются
  реализации при создании. `explanation_call_id` ссылается на сохранённый вызов.
- `TaskInput` содержит только ID, имя модуля, описание и `.cfg` как текст.
  Метаданные происхождения `TaskMetadata` используются подготовкой/аудитом,
  но не передаются в LLM. Пути Gold не входят в интерфейс генерации.

Статусы проверки: `passed`, `spec_error`, `timeout`, `tool_error`, `not_run`.
Таймаут не равен доказанной ошибке спецификации; технические результаты
анализируются отдельно. Для `not_run` команда пуста, exit_code равен null,
вывод пуст, duration_seconds равен 0. Неизвестная категория ошибки — null.
Время измеряется монотонными часами. Полные stdout и stderr сохраняются отдельно,
без нормализации и обрезки; правило объединения для обратной связи фиксирует фильтр.

`LLMResponse.model` — реально сообщённая провайдером модель; запрошенный ID и
параметры сохраняются в запросе. Usage неизвестен — null, а не 0. Raw response
не содержит токенов авторизации или HTTP-заголовков с секретами.

## Предлагаемое размещение

```text
results/<experiment-id>/
  manifest.json
  calls/<call-id>/request.json
  calls/<call-id>/response.json
  calls/<call-id>/record.json
  tasks/<task-id>/repeat-01/initial/Spec.tla
  tasks/<task-id>/repeat-01/initial/verification.json
  tasks/<task-id>/repeat-01/A/attempt-01/record.json
  tasks/<task-id>/repeat-01/A/attempt-02/Spec.tla
  tasks/<task-id>/repeat-01/A/attempt-02/verification.json
  tasks/<task-id>/repeat-01/A/attempt-02/feedback.json
```

Аналогично B/C. Все пути в записях относительны корню эксперимента и не выходят
за него. Идентификаторы безопасны как компоненты пути; writer обязан проверять
это. Новые результаты не перезаписывают существующие.

`manifest.json` фиксирует schema_version, experiment_id, phase (`pilot`/`main`),
UTC-время, revision и признак dirty tree, полный снимок протокола/настроек,
версии Python/Java/JAR, SHA-256 JAR, источники и хеши файлов задач/промптов,
версию фильтра и политику сбоев. Основной запуск требует заполненного manifest.
Полные команды и логи лежат в результате верификатора; запись на диск должна
сохранять их без потерь. Все значения enum сериализуются как строки.

`CallRecord` — один фактически завершённый вызов с уникальным `call_id`.
`AttemptRecord` — одна версия спецификации в одной ветви с ссылкой на вызов.
Первая попытка всех трёх ветвей ссылается на один начальный `call_id` и общие
начальные артефакты. Это три учётные попытки, но один реальный API-вызов.
В `feedback_path` хранится обратная связь, использованная для этой попытки;
для первой попытки поле равно null. Объяснение имеет собственный `CallRecord`
с purpose `explanation` и не является новой попыткой основной модели.

Общий расход эксперимента считается по уникальным call_id. При сравнении
ремонта начальные расходы показываются отдельно; любое распределение общей
стоимости по ветвям явно маркируется. Нельзя складывать расходы трёх ссылок
на один вызов как три реальных вызова.

Технические неуспешные API-запросы сохраняются как отдельные события с ID,
категорией, временем и доступным usage: отсутствие ответа не доказывает нулевой
расход. Они не создают AttemptRecord. Ошибки сохранения данных останавливают
запуск; их нельзя скрывать и продолжать как при полном наборе артефактов.

## Задачи

Каждый каталог `tasks/<task-id>/` содержит описание, Gold, исходную конфигурацию
и metadata.json с полями `TaskMetadata`. Полный commit SHA, пути и ссылки должны
вести к закреплённому источнику. Дополнительные TLA+ модули учитываются отдельно
с хешами; имя основного модуля должно совпадать с именем файла. Любая адаптация
конфигурации документируется и хешируется, исходник сохраняется отдельно.
